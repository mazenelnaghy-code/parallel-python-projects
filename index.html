Our plan: 3 versions of the same program

1. Sequential

One core does all the work, one piece after another.

2. Parallel, done well

Big chunks of work split across 4 cores. Genuinely faster.

3. Parallel with overhead

Work cut into thousands of tiny tasks. Slower than sequential, which shows the overhead from Lecture 2.

Matrix multiplication

WhatC = A × B. Each cell of C = one row of A times one column of B. SplitEach process computes some rows of C. FlynnMIMD hardware, data-parallel method (same formula on different rows).
OverheadEvery process needs all of matrix B. Sending big B again and again means big messages (Lecture 2).
FixSend B once per process and give each process many rows. Write the loops by hand: NumPy is already optimized and would hide the effect.

Game of Life

RulesEach cell looks at its 8 neighbours. A live cell with 2 or 3 live neighbours stays alive. A dead cell with exactly 3 becomes alive. All other cells die or stay dead. SplitThe grid is cut into 4 colored strips, one per process. FlynnMIMD hardware, data-parallel method (same rule on every cell). Hard partCells on a strip's edge (dashed lines) need neighbours from the next strip. After every step, processes swap these border rows, and all must finish before the next step.
OverheadMessages and waiting at every single step. On a small grid this is slower than sequential. This is the distributed-memory message passing from Lectures 2 and 4.
FixA big grid (more work per step), or shared memory so borders don't need to be sent. Too much for Sunday, a good idea for later.

Why processes, not threads?

Standard Python lets only one thread run Python code at a time (the GIL). For heavy calculations, threads give no speed-up, so we use the multiprocessing library: separate processes, one per core.

More processes, how much faster?

  • Never 4× with 4 cores: splitting, sending and collecting cost time. Her OS slides say it too: "speed-up with N processors is less than N".
  • 1 process is slower than sequential: it pays the overhead with no extra core.
  • 8 processes barely help: the laptop has 4 real cores, and the extra 4 are hyper-threads sharing them.

The top and bottom strips finish in 0.3 s, then those cores wait for the middle strips. Many small chunks keep all 4 cores busy until the end.

Where the overhead comes from

  • The laptop's RAM is shared (UMA), but each Python process has its own memory.
  • So tasks and results travel as messages, like the distributed-memory model in Lecture 2.
  • Every message costs time to package and send. That's the communication overhead.

Speed-up in numbers

Speed-up = Tsequential ÷ Tparallel = 3.47 ÷ 1.53 = 2.27×Efficiency = speed-up ÷ cores = 2.27 ÷ 4 = 57%

A perfect 4× (100%) is impossible in practice. The missing 43% is the overhead (starting processes, sending tasks, collecting results) plus the laptop slowing its clock when all 4 cores are busy.

Starter code (Mandelbrot, all 3 versions)

The same code we used for the timings above, cleaned up. Save it as mandel.py and run python mandel.py. When we ran this exact file: sequential 3.60 s, parallel 1.48 s (2.43× faster), overhead version 29.23 s (20× slower, on purpose).

# Sequential vs parallel Mandelbrot: 3 versions + timings
import time
from multiprocessing import Pool

W, H, MAX_IT = 640, 420, 200

def escape_count(cr, ci):
    zr = zi = 0.0
    n = 0
    while zr * zr + zi * zi <= 4.0 and n < MAX_IT:
        zr, zi = zr * zr - zi * zi + cr, 2 * zr * zi + ci
        n += 1
    return n

def mandel_row(y):
    # one task = one whole row (good parallel)
    ci = -1.2 + 2.4 * y / H
    return [escape_count(-2.2 + 3.0 * x / W, ci) for x in range(W)]

def mandel_pixel(xy):
    # one task = one pixel (overhead version)
    x, y = xy
    return escape_count(-2.2 + 3.0 * x / W, -1.2 + 2.4 * y / H)

if __name__ == "__main__":   # needed on Windows
    t = time.perf_counter()
    seq = [mandel_row(y) for y in range(H)]
    t_seq = time.perf_counter() - t

    t = time.perf_counter()
    with Pool(4) as pool:
        par = pool.map(mandel_row, range(H), chunksize=4)
    t_par = time.perf_counter() - t

    pixels = [(x, y) for y in range(H) for x in range(W)]
    t = time.perf_counter()
    with Pool(4) as pool:
        tiny = pool.map(mandel_pixel, pixels, chunksize=1)
    t_tiny = time.perf_counter() - t

    assert par == seq                                   # same picture
    assert tiny == [n for row in seq for n in row]
    print(f"1. Sequential: {t_seq:.2f} s")
    print(f"2. Parallel:   {t_par:.2f} s  ({t_seq / t_par:.2f}x faster)")
    print(f"3. Overhead:   {t_tiny:.2f} s  (268,800 tiny tasks)")

How to prove it live in the session

  1. Open Task Manager (Ctrl + Shift + Esc) → Performance → CPU. Right-click the graph → Change graph to → Logical processors.
  2. Run the sequential version: only one core's graph jumps up.
  3. Run the parallel version: all cores jump up together. That is the parallelism, visible.
  4. Show the same result: the assert lines prove both versions produce the exact same picture.
  5. Show the numbers: times, speed-up and the overhead version being slower.
  6. Keep the laptop plugged in, and run each version 2–3 times for steady numbers.

Key words, explained simply

Speed-up

How many times faster the parallel version is: sequential time ÷ parallel time.

Overhead

Extra time that parallel adds: starting processes, sending tasks, collecting results. Lecture 2 calls it communication overhead.

Chunk size

How much work goes in one task. Too small: too many messages. Too big: some cores sit idle at the end.

Load balancing

Giving every core a similar amount of work so none waits for the others (Lecture 4).

Process vs thread

A process has its own memory; threads share one. In Python, only processes run heavy calculations on several cores at once.

GIL

Python's lock that lets only one thread run Python code at a time. The reason threads don't speed up calculations.

MIMD

Multiple instructions, multiple data. Each core runs its own instructions on its own data. Multi-core PCs are MIMD (Lecture 2).

Data parallelism

The same operation on different pieces of data at the same time. The SIMD idea, done here in software.

How we'll explain it in the session

  1. Why this project: heavy, independent work. Each piece can be done on its own, so cores can share it.
  2. Flynn type: our laptop is MIMD (a multi-core PC, Lecture 2). Our method is data parallelism: the same operation on different data.
  3. Memory: shared RAM (UMA), but separate memory per Python process. Data moves as messages.
  4. Speed-up: 2.3× on 4 cores, not 4×, because of overhead and slower clocks when all cores are busy.
  5. Overhead: tiny tasks mean thousands of messages, and the delivery costs more than the work.
  6. Fix: bigger chunks, send names instead of data, small chunks for load balancing.
